# 第 23 章 抽取与评测

第八部分从这里开始。调度解决「何时发请求」；本章解决「响应里的字段如何变成数仓里的行」，以及改版之后如何知道解析器坏了。原则只有一句：**规则优先、模型兜底。** Agent 何时上场、cost per action 多贵，是第 24 章。

Mitchell 书里的 NLP、用爬虫测网站，不是本书主线。这里的模型只做抽取与分类，对象是你们 Demo 或许可明确的页面/JSON。敏感字段不上公有云（23.3）。

## 23.1 规则优先、模型兜底

稳定接口（JSON / Protobuf / 固定 CSS）用规则：路径、字段名、编号写进第 10.1 节和解析器代码。规则便宜、可 Diff、可进 CI。改版时黄金集一红，人能指出是哪条选择器。

模型出场的条件要写死，例如：

- 规则置信不足：必填字段空了，但 HTTP 仍是 200、也不像第 6 章挑战页。
- 结构是自由文本或多模板 HTML，合同允许抽，规则覆盖成本明显高于抽样评测。
- 已有黄金集，模型在集上的指标达到门槛才进 worker，而不是「感觉能抽」。

不要默认「每条响应都送给大模型」。那会把第 22.2 节的费用列打满，且把正文送出机房（23.3）。也不要用模型去过验证码或猜签名——那是第 6、10 章的问题。

规则与模型的交接：规则先跑；失败样本进旁路队列，模型或人工标一遍，再决定是修规则还是接受模型输出。模型输出必须能对照 Schema 校验，通不过当失败，不要静默写进仓储。

## 23.2 Schema 与黄金集

**Schema。** 每个产品线一份：字段名、类型、是否必填、主键、是否可能含个人信息。和 10.1 的响应形状对齐。解析器、模型、仓储、API 出数都认这一份。缺 Schema 就谈不上评测，只能「看起来有数」。

**黄金集。** 脱敏后的原始响应（HTML / JSON / proto 文本）+ 期望抽出的行。来源是你们 Demo 或授权样本，不是从第三方生产环境扒一堆。数量不必大，要覆盖：正常列表、空列表、末页、一种业务错误码、一次改版前的旧模板（若还要兼容）。

评测在 CI 里跑：规则解析器对黄金集做**精确匹配**或字段级对比；上模型时另报准确率 / 漏抽率，门槛不达标禁止部署。解析器版本号写进血缘（第 21.3 节）。改规则必须先改黄金集或接受测试失败——禁止「先上线再补样例」。

Diff 是日常工具：新旧解析器对同一批原始响应出两份表，看哪几行变了。第 24.1 节的助手可以摘要 Diff，但不能代替黄金集门槛。

## 23.3 成本与敏感字段不上云

抽取也有每成功动作成本：CPU、模型 token、人工校对。规则几乎为零；云上大模型按 token 计，长 HTML 一次可能贵过整次 HTTP。预算和出口、云手机放在同一张表（第 22.2 节）。日配额打满则模型旁路停，规则继续。

**不上云的：** 身份证号、手机、精确地址、Cookie / Token、未脱敏的用户生成内容、密钥、实验日志里的会话。能在规则阶段丢掉的字段，不要进模型提示词。必须用模型时：本地或专有区域、脱敏后再发、合同允许的供应商；默认是否。

落盘仍守第 1.4 节：能存、期限、谁能看。模型提供商的训练用途条款要读；不允许拿你们样本去训对方基础模型时，就不要用那条 API。

判断句：**黄金集决定能不能发版；Schema 决定能不能存；敏感字段决定能不能出机房。** 下一章把模型和脚本收成助手与路由，并给 Agent 画一条成本边界。

# 第 17 章 JNI、so 与调起（自研 so）

[第 16 章](ch16-frida.md)在 Java 层打了请求前日志。有的 Demo 把 HMAC、Protobuf 编解码放进 `.so`，jadx 里只剩 `native` 声明。本章只分析**你们自己编译的、密钥和源码都在仓库里的教学 so**。用 Frida、unidbg 从**第三方** so 里提取密钥或签名算法，第 1.5 节不写；17.4 再划何时停手。

采集要的仍是 10.1 文档和能在测试环境复现的规则。native 只是实现位置变了，不是换一条可以对抗商店包的技术线。能在服务端或共享 C 库里看到同一套校验，就不要反汇编。

## 17.1 JNI 与加载

JNI 是 Java 调 C/C++ 的官方桥。对采集有用的只有加载和声明，不需要把 JNI 规范背完。

**加载。** `System.loadLibrary("demo")` 会按 ABI 找 `lib/arm64-v8a/libdemo.so` 等（第 12.3 节地图）。`JNI_OnLoad` 里可以 `RegisterNatives`，也可以依赖默认导出名。Debug 构建把 so 和 APK 成套归档：缺了对应 ABI，对照抓包会误判「没有 native」。

**声明。** Java 侧 `native byte[] hmac(String canonical);`，实现要么在 `Java_com_example_demo_Sign_hmac` 这种导出符号里，要么在 `RegisterNatives` 登记的函数里。第 13 章落到 `native` 就停在这一层：记下方法名、哪个 so、哪个 ABI，不要在 jadx 里猜机器码。

**密钥从哪来。** 教学 so 的测试密钥走环境变量或构建配置（第 7.9、10.3 节），与生产隔离。不要把生产密钥编进 `.rodata` 再「练习找」。生产若真把密钥只放 so 里，那是产品问题，采集侧用测试密钥和测试服，不要去抠上架包。

iOS 的 `.dylib` / xcframework、鸿蒙的 native 库，加载方式不同，纪律相同：只分析你们构建的那一份。

## 17.2 导出符号识图

对象是 CI 打出的 `libdemo.so`，不是商店包里剥出来的无名 so。识图用系统自带的只读工具即可：[readelf](https://sourceware.org/binutils/docs/binutils/readelf.html)、`nm`、Android NDK 的 `llvm-readelf`。Ghidra / IDA 可以打开**你们的** so 看导出表，不是为了还原第三方算法（第 13.4 节边界仍在）。

看什么：

- **文件与 ABI：** 路径是否匹配 12.3 的 `lib/<abi>/`。
- **导出名：** 是否有 `Java_包_类_方法`；没有则可能是 `RegisterNatives` 或符号被 strip。strip 了就回源码和 `JNI_OnLoad`，不要靠猜。
- **依赖：** 链了哪些系统库。教学 so 保持短：链接官方 crypto（如 BoringSSL / 系统 API），不要模仿商业加固 so 的名字。

产出是一页纸：so 文件名、ABI、Java `native` 方法 ↔ 导出符号或注册表。这页纸进 10.1 的「调用点」，和抓包路径放在一起。字符串里若出现 Host、路径，当锚点；**不要**把 `.rodata` 当第三方密钥猎场。

没有源码、符号全无、还不是教学 so：这不是识图失败，是 17.4 的停手条件。

## 17.3 正常 JNI / 教学 Frida 调起 / RPC·模拟执行的边界

三种手段由易到难，越往后越不该成为采集默认栈。

| 手段 | 是什么 | 本书里何时用 | 边界 |
|------|--------|--------------|------|
| **正常 JNI** | Java 调你们的 `native`，源码、测试密钥、服务端校验都在仓库 | 默认。CI 给 so 做与 Java 相同输入的单测 | 不要为了「看起来像逆向」跳过源码 |
| **教学 Frida 调起** | 在自有 Debug 进程里，对**已导出的教学符号**打日志，或主动调一次你们的 `hmac` | 第 16 章的 native 对应物：看参数、返回值是否与抓包 `sign` 一致 | 只调教学 so 的导出函数；不写对第三方 so 的 `NativeFunction` 扫盲调用 |
| **RPC / 模拟执行** | 把 so 当黑盒在设备外跑（RPC 到真机，或模拟器/unidbg 一类） | 名词级：知道有人用它在 PC 上跑 native。自研 so **更应该**抽成可在 CI 跑的 C/Rust 单测或小命令行 | **不写** unidbg / 模拟器跑第三方 so 的步骤；不从商店 so 抽算法到采集脚本 |

教学 Frida 调起仍遵守 16.2：打印规范化字符串或返回的 hex，不打印密钥；能改 so 打日志就改源码。主动 `NativeFunction` 调用等于在进程里跑你们自己的函数，和单元测试同构，不是「破解」。

模拟执行对第三方 so 的吸引力是：不用真机也能算 `sign`。那正是第 1.5 节禁止的「从第三方 so 提取算法」。你们自己的算法，在仓库里用同一份 C 代码编一个 `demo-hmac` 命令行，输入 canonical、输出 hex，采集脚本调它或用同语言重写并单测——这比模拟执行可审计得多。

## 17.4 何时不该继续砸 so

看见 `native` 不要自动进入反汇编。下面任一成立，就停：

1. **不是自研 / 教学 so。** 第三方商店包、合作方未授权分析 native、来路不明的 `.so`。
2. **源码和测试密钥已经能复现。** 第 10.3 节过了，so 只是实现细节，不必再砸。
3. **符号剥尽、控制流明显做了保护，目的只剩掏密钥。** 记现象，换未保护的教学构建，或停手。不写 OLLVM 还原、不写内存里抠密钥。
4. **逻辑可以放到服务端或官方 API。** 采集走合法客户端，不依赖从设备里还原的算法。
5. **砸 so 的成本已经高于换协议。** 第 14.3 节同一句：换未加固 Debug、换官方接口、看网关日志，或停。

「继续砸」在采集工程里几乎没有正期望值：即使算出第三方 `sign`，授权、账号、出口问题一个没解决，脚本也不能上生产任务。把时间留在 10.1 文档和第 18 章回流。

第 14.5 节的 dump、unpinning、绕过反调试，对 so 同样适用，这里只引用，不展开。

## 17.5 出门考：自研教学 so

同一 Demo、同一测试服：Java 层把「规范化之后」交给你们写的 `libdemo.so` 做 HMAC（或等价摘要）。测试密钥不进 Git。

1. 写出加载链：`loadLibrary`、ABI、Java `native` 声明对应的导出符号或 `RegisterNatives`（17.2 一页纸）。
2. 用**源码或 CI 单测**（正常 JNI）对固定 canonical 得到固定 hex；再抓一条列表，中间人里的 `sign` 与之对上（可叠加第 16 章请求前日志）。
3. 说明三种手段你实际用了哪一种；若用了教学 Frida 调起，钩的是你们的导出符号。**没有**对第三方 so 做模拟执行或掏密钥。
4. 用 17.4 写一句：什么情况下会停手而不是继续反汇编。

通过即可。第五部分的阅读到 so 为止。分析产出要进任务配置，不要停在笔记里。

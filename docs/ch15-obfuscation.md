# 第 15 章 混淆与还原（自有包）

[第 14 章](ch14-hardening.md)的壳让 DEX **不在**明文里。混淆是另一回事：DEX 还在，jadx 能打开，只是类名、方法名变成 `a.b.c()`，控制流难看，字符串有时被加密。本章只处理**自有包**：辨认类型、用 CI 的 `mapping.txt` 还原到可读可审计，再拿资源和 Protobuf 跟[第 10 章](ch10-protocol.md)抓包对照。

对象仍是第 12.1 节三种制品。商店随手包、没有 mapping 的第三方 Release，不进还原台。目标不是把别人的加固解开，也不是导出一份可重新编译的「源码」。Frida 对照留给第 16 章；逻辑在 so 里留给第 17 章。

有仓库源码时，先读源码和未混淆 Debug。Release 开 R8，是为了核对「上架的那一份」和文档是否仍对得上，不是为了每天在混淆代码里办公。

## 15.1 混淆类型辨认

先看现象，再选手段。壳与混淆可以叠：先按第 14 章判断有没有 stub；有明文 DEX 再看下表。名称以 Android [R8 / 缩减文档](https://developer.android.com/build/shrink-code) 和你们构建日志为准，「第几代混淆」没有标准定义。

| 类型 | 你在 jadx 里看见什么 | 采集侧怎么应对（自有包） |
|------|----------------------|---------------------------|
| 标识符重命名 | 包名变成 `a.b`，方法 `a()`、`b(c)` | CI 归档的 `mapping.txt` + retrace（15.2）。搜抓包里的**路径和 JSON 键**，不要猜类名 |
| 收缩（shrink） | 某类「源码里有、包里没有」 | 没被引用的代码没打进去，不是丢了。要分析的协议层加 `-keep`，或看未缩减构建 |
| 优化 / 内联 | 几个方法合成一坨，协程状态机更乱 | 换 `minifyEnabled false` 的 Debug；不要在优化后的 smali 里还原业务语义 |
| 字符串加密 | `/v1/items` 搜不到，运行时才拼出来或从 native 取 | 关这项再打一包，或用 Debug 日志（第 10.3 节）。不写对第三方的字符串解密器 |
| 控制流平坦化 | 满屏 `switch (state)`、无意义 goto | 换未开启这项的构建。不写反平坦化脚本 |
| 反射 / 动态类名 | 类名在字符串或资源里，不在直接调用 | 仍以抓包路径为锚；字符串若被加密，回到上一行 |
| Kotlin 元数据 / 协程 | `Continuation`、状态机编号 | mapping + 源码；反编译难看不等于协议变了 |

商业混淆器（DexGuard 等）常把上表几行叠在一起，再加壳。辨认仍然用现象。**没有 mapping、不是你们的包：停。** 不要上「通用反混淆」工具去练手。

和相邻概念再对一次：

- **壳：** 业务 DEX 不在，见第 14 章。
- **混淆：** DEX 在，名字没了。
- **Protobuf / JSON 键：** 线上字段名或编号往往**不会**跟 Java 标识符一起被 R8 改掉（见 15.3）。所以抓包仍是第一锚点。
- **13.6 历史未混淆包：** 当前 Release 读不动时，先用旧的 `minify` 关闭构建读懂协议，再对照当前 mapping。

iOS 的 Swift 名字改编、去符号，纪律相同：用你们的 dSYM / 未剥离构建，不写对商店包的符号还原。鸿蒙同理。

## 15.2 还原目标：可读、可审计

还原不是「得到一份能编译的工程」。采集要的是两句话能讲清、三个月后能复查：

- **可读：** 人能指出「这条列表请求在哪个类的哪个方法里拼出来」，并和 10.1 文档对上。
- **可审计：** 另一人拿同一 APK、同一份 `mapping.txt`、同一条抓包，能复现你的指向。mapping 和 APK 一样要记哈希、构建号（第 12.1、18 章）。

正路只有一条：**构建系统给你的 mapping。** Android 上 R8 在 `minifyEnabled true` 时写出 `mapping.txt`（以及可选的 `seeds.txt`、`usage.txt`）。把 mapping 和 APK **成套归档**，缺一不可。用 SDK 的 retrace（或 R8 自带的 retrace）把崩溃栈、jadx 里的 `a.b.c` 映回源码名。jadx 也可以加载 mapping，显示还原后的名字——仍只加载你们自己的文件。

顺序：

1. 确认 APK 与 mapping 是同一次 CI（文件名、构建号、哈希）。对不上就换，不要「找一份差不多的 mapping」。
2. 用 10.1 的不变量在 jadx 里搜到调用点（路径、头名、JSON 键、proto 消息名）。
3. retrace / 加载 mapping，把混淆名写回源码名，抄进接口文档。
4. 能对上源码或 Debug 日志就停。不要继续还原无关模块。

**不要当还原的：** 没有 mapping 就对第三方 Release 跑反混淆器；把整包反编译树当源码备份；为了「更可读」去改 smali 再重签。合作测试包若对方能给 mapping 或未混淆构建，要那两样；只给加固混淆包时，走第 14.3 节的换协议 / 停手，而不是自造 mapping。

密钥、HMAC 实现若只在混淆后的 Release 里、仓库与 Debug 都没有：那不是混淆问题，是第 12.4 节你不该分析这个包，或应回到服务端校验代码（10.3）。

## 15.3 资源 / protobuf 与抓包对照

混淆改的是**客户端符号**，线上形状以抓包为准。对照可以少读很多 `a()`。

**JSON。** Gson / Moshi / kotlinx.serialization 通常用注解或默认字段名决定线上键。R8 重命名的是 Java 属性，`@SerializedName("cursor")` 里的 `"cursor"` 还在。抓包里看见 `cursor`，就搜这个字符串，不要搜混淆后的 `a`。keep 规则若没保住序列化类，表现为「包能装、请求字段缺了」——那是你们构建配置的 bug，用未缩减包或修 keep，不要在采集脚本里猜被删掉的字段。

**Protobuf。** 线上是字段**编号**，不是 Java 名。文档写消息名和 `.proto` 路径（10.1）。包里若带 `assets` 或 `proto` 描述符，和抓包 hex 对编号；Java 类名被 R8 改了不影响编号。没有描述符时，用你们仓库里的 `.proto`，不要从第三方包「猜编号含义」。

**资源与 assets。** `res/values`、渠道配置、内置 Host、证书，常常仍是明文（资源加密是第 14.2 节另一档）。apktool 解码自有包（第 13.3 节）看配置，和抓包 Host 对一下，比在混淆代码里搜常量快。

**对照作业（同一 `versionCode`）：**

1. 抓一条列表：记下路径、JSON 键或 proto 编号。
2. jadx（加载 mapping）落到拼请求处。
3. 三列并排：抓包字段、源码 / 还原后的名字、资源或 `.proto` 里的定义。对不上的那一列才值得深挖（进 so、字符串加密、或单纯文档写错）。

产物仍是补全后的 10.1，外加「还原所用 mapping 的哈希」。不要产出一份「反混淆源码仓库」。

## 15.4 出门考：自有混淆 Demo

同一 Demo、同一测试服，CI 打出两份：`demo-plain`（`minifyEnabled false`）和 `demo-minify`（R8 开启，**归档 mapping.txt**）。不要用商店里别人的包。

1. 指出 `demo-minify` 属于 15.1 的哪些类型（至少要有标识符重命名；若你还开了字符串加密或收缩，分别写现象）。
2. 在 `demo-minify` 的 jadx 里用列表路径或 JSON 键定位调用点；用 mapping retrace 成源码名，写进 10.1。换一个人只拿 APK + mapping + 抓包，应能指到同一方法。
3. 做一次 15.3 对照：抓包字段、还原后的代码、资源或 `.proto` 三列一致。
4. 说明你**没有**对第三方包做反混淆，也没有在无 mapping 时「猜」类名当结论。

通过即可。静态阅读到这里：壳换构建，混淆用 mapping。还对不上、且只在运行期才出现的值，再进第 16 章——在**自有 Debug 包**上用授权调试器看请求前日志，而不是给 Release 壳「揭秘」。

# 第 10 章 协议、签名形态与增量

第 9 章把流量接到了。本章把它收成**可重放的说明**：路径、字段、哪些每次都会变、分页和增量怎么走。签名只在**自有 Demo** 上复现——你有服务端校验代码和 Debug 日志。从第三方 so 里掏密钥或算法，本书不写（第 1.5 节）。

抓包会话本身不是文档。换一台设备、过一天，对照不上的字段就是协议的一部分，不是「Charles 坏了」。

## 10.1 从抓包到接口文档

对每一条要采的业务，留下一份别人按它能写出客户端的说明。建议至少有：

| 项 | 记什么 |
|----|--------|
| 身份 | App 版本、是否 Debug、账号角色（第 7 章）、出口租约 |
| 传输 | REST / gRPC / 长连接；Host；TLS 在哪终结（第 9.2 节） |
| 请求 | 方法、路径、查询、头（鉴权头单独标出）、body 形状（JSON 字段或 proto 消息名） |
| 变化 | 连续两次「同一操作」里，哪些字段变了（留给 10.2） |
| 响应 | 成功形态、业务错误码（即使 HTTP 200）、空列表与末页怎么表示 |
| 样本 | 一条脱敏后的请求/响应，能进 Git 或附件；密钥不要进样本 |

Protobuf 写消息名和 `.proto` 路径，不要只贴 hex。gRPC 写 service / method。长连接写：如何握手、列表是一帧还是推送、心跳间隔。

文档的读者是三个月后的你，以及第 18 章钉版本的人。路径没变、签名规则变了，要能看出来是协议变更而不是采集写错。

先把**只读列表 / 详情**写成文档。写操作、支付、会改对方数据的接口，默认不进采集任务（第 1.3 节）。

## 10.2 时间戳、nonce、body hash：如何辨认

同一操作抓两次（同一 Debug 包、同一账号、间隔几秒）。把两次请求并排，字段分成三类：

- **不变：** 路径、方法、大部分业务参数。这是接口的骨架。
- **随会话变：** Token、设备 ID、游客令牌。跟第 7、5 章租约走，不要写进「签名算法」。
- **随每次请求变：** 常见名字是 `ts` / `timestamp`、`nonce` / `once` / `random`、`sign` / `sig` / `signature`、`hash`。这是防重放和完整性，不是业务字段。

辨认用现象，不靠猜缩写：

**时间戳。** 两次相差大约等于你两次点击的间隔；量级像 Unix 秒（10 位）或毫秒（13 位）；服务端过期窗口往往几十秒到几分钟。时钟不准会表现为「偶发验签失败」。采集机要 NTP；不要把过期窗口当成可以无限重放的缓存。

**nonce。** 每次不同、同一秒内也不该重复；有的服务端会记住最近用过的值。重放整包（含旧 nonce）会失败，这是设计如此。采集侧每次请求新生成，不要复制抓包里的那一串。

**body hash / 签名。** 改 body 里一个字符，这一字段变；只改无关头，它可能不变。常见是对「规范化后的 body 或字段拼接」做摘要或 HMAC。规范化包括：键排序、空格、编码、是否含 token。两次抓包对不上时，先对**规范化规则**，不要先换哈希算法。

**还可能看到：** 请求 ID、客户端版本号进签名字符串、设备指纹摘要。版本号要钉死（第 18 章）；设备摘要和出口、账号绑在一起，不要每次随机造（第 7.6、8.1 节的伪造游客是红线）。

这一节的产出是文档里的「变化字段表」，不是一份对第三方生效的 `sign.py`。第三方包里算法在 native 里时，停在辨认：知道「有签名、随请求变、校验失败长什么样」。怎么算，只在 10.3 的 Demo 上写。

## 10.3 在自有 Demo 上复现签名

复现的对象是**你写的校验函数**，不是商店里某个 App。

顺序：

1. 打开 Demo 服务端（或共享库）里验签的代码：拼接顺序、编码、密钥从哪读。
2. Debug 构建打一行日志：规范化之后、哈希之前的那串字符串（注意不要把密钥打进日志）。
3. 用同一串在采集脚本里算一遍，和 App 抓到的 `sign` 对上。
4. 密钥放环境变量或密钥服务（第 7.9 节），与生产密钥隔离。测试密钥只验测试环境。

对得上，说明文档里的规范化规则是对的，脚本可以当合法客户端发**只读**请求。对不上：先对日志里的明文，再对时钟和编码，不要怀疑「是不是要上 Frida」。Demo 的密钥你已经有，不需要从 so 里挖。

合作测试包若对方提供了验签说明或测试密钥，按对方文档做，并写进授权记录。只给了包、不给规则时：用他们的抓包通道当黑盒，或请他们开放服务端日志；不要把第五部分的教学手段用到他们的生产加固上。

脚本里的签名函数要有单测：固定输入 → 固定输出。App 升版后先跑单测和黄金样本（10.1），再跑采集。

## 10.4 分页、增量、推送

稳定拉数比「签过名」更常翻车的是：**同一条记两次，或漏一段。**

**分页。** 三种常见：页码、`cursor` / `next_token`、`since_id`。页码在插入新数据时会漏或重；能用游标就用游标。末页要写进文档：空数组、`has_more=false`、还是特定错误码。并发翻页必须幂等（第 3.6 节）：主键相同则覆盖或跳过。

**增量。** 用服务端提供的水位：`updated_at`、changelog、消息 ID。本地存「上次成功的水位 + 当时 App 版本」。全量只做底仓或对账，不要当默认调度。水位回退（对方修数据、时区搞错）要能发现，而不是静默少一批。

**推送。** 长连接推增量时，采集是「连上、校验、落盘、断线重连从水位接着」，不是把每条推送当独立爬取任务。心跳失败按会话过期处理：重新握手，不要拿旧帧里的签名去重放。对方若同时提供 REST 增量，优先 REST，推送当加速，对账仍靠水位。

存储沿用第 3.5 节：每条带业务主键、抓取时间、原始或规范化字段，能和旧文件 Diff。协议一变，Diff 比「感觉数据少了」更早报警。

## 10.5 出门考：Demo App 稳定拉数

在你控制的 Demo App + 服务端上完成：

1. 按 10.1 写出列表接口文档，含两次抓包的变化字段表（10.2）。
2. 用服务端验签代码或 Debug 日志，在脚本里复现签名，单测通过；密钥不在仓库里。
3. 脚本拉完整列表（或两页以上），主键不重复；再改一条服务端数据，增量能发现（10.4）。
4. 故意把时钟拨偏或重放旧 nonce：失败可解释，而不是「有时 200 有时 403」。
5. 用一句话说明：为什么这段签名代码不能拿到第三方 App 上用。

通过即可进第 11 章。仍有必须点几下才出的请求，用 UI 触发拿会话，批量还走本章的协议。

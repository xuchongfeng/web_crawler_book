# 第 13 章 静态工具链

[第 12 章](ch12-artifacts.md)已经钉住制品：同一份 CI / 上架 / 合作测试包，哈希和抓包版本对得上，并且 12.4 判定「值得打开包」。本章只做一件事：按任务选静态工具，在**同一份 Demo** 上走出「路径 → 调用点 → 写回[第 10 章](ch10-protocol.md)文档」的主路径。

对象仍是第 1.5 节。商店随手包、来路不明的安装包，不进 jadx。加固壳、商业脱壳、从第三方 so 掏算法，不在本章（第 14、17 章和第 1.5 节）。有仓库源码和 R8 `mapping.txt` 时，先对源码，反编译只用来核对「包里是不是这份」。

工具的官方文档会变。下面记的是**分工**，菜单以你本机版本为准。

## 13.1 任务 → 工具

先写任务，再开软件。没有「要对照的那条请求」，全局反编译是在通读别人的工程，对采集没有产物。

| 你要回答的问题 | 优先用 | 不要一上来就 |
|----------------|--------|----------------|
| 包名、版本、组件、权限、deeplink 是否和抓包一致 | Android Studio [APK Analyzer](https://developer.android.com/studio/build/apk-analyzer)、SDK 的 `apkanalyzer`、[apktool](https://apktool.org/) 解 Manifest | 把整个 DEX 反编译一遍 |
| 抓包里的路径、头名、JSON 键、proto 消息名在 Java / Kotlin 的哪 | [jadx](https://github.com/skylot/jadx) 搜索 | 猜类名；对着混淆后的 `a.b.c` 从入口 Activity 读起 |
| 资源、二进制 XML、assets 里的 Host / 证书 / 配置 | apktool 解码（仅自有包）；APK Analyzer 看 `assets/` | 把资源当「隐藏的签名算法」 |
| 调用图、交叉引用、重度混淆后的控制流还想看 | 13.4 的 JEB 等；仍只针对授权包 | 为了「专业」上付费套件拆商店包 |
| 逻辑在 `.so` 里 | 记下 JNI 名，去第 17 章 | 本章用 jadx 硬读 hex |
| DEX 是壳、Application 是 stub | 记现象，去第 14 章 | 本章找「一键脱壳」 |

同一任务可以两件工具：Analyzer 看结构，jadx 搜字符串。选贵的、选能改 smali 的，都不提高采集成功率。选**哪一份构建**也是任务：当前包读不动时，先看 CI 里的历史版本（13.6），不要先换更重的工具。

## 13.2 jadx

[jadx](https://github.com/skylot/jadx) 把 DEX 反编译成近似 Java。GUI（`jadx-gui`）适合跟着抓包跳；CLI（`jadx -d out demo.apk`）适合把一份构建的文本放进仓库旁的分析目录——仍然只放**你们的包**。

采集里真正用到的就三下：

1. **打开第 12 章那份 APK**（或拆好的 DEX），不要混进另一个渠道包。可以是当前构建，也可以是同一产品线 CI 里的历史构建（13.6）；打开的那一份必须和本次抓包的 `versionCode` 一致。
2. **按 10.1 文档里的不变量搜：** 路径片段（`/v1/items`）、鉴权头名、JSON 键、proto 消息名、Host。混淆改的是类名，字符串和路径常常还在。
3. **从字符串跳到用法（Find usage），读拼请求的那一层：** OkHttp 拦截器、Retrofit 接口、手写的 `Request.Builder`。记下：哪些字段在 Java 里拼、哪些进了 `native` 方法。

Kotlin 协程、内联、R8 之后，反编译会很难看。对不上时：用你们 CI 产出的 `mapping.txt` 把混淆名还原（第 15 章会展开）；或回到 Debug 未混淆构建。不要把「jadx 读不懂」理解成「必须上 Frida」。Debug 日志和第 10.3 节的服务端验签仍然更便宜。

**边界。** jadx 给的是阅读件，不是可编译的源码工程。不要导出整棵树当「源码备份」，更不要拿它去还原第三方密钥。搜到 `SecretKey` / `hmac` 而对象不是自有 Demo：停，回到 12.4——你可能不该分析这个包。搜索无命中且 Manifest 里 Application 像壳：去第 14 章，不要在 jadx 里换十种反编译选项碰运气。

有源码时，jadx 的价值是：**确认上架包和仓库是同一提交**，以及 Release 开了混淆之后，字符串是否还对得上抓包。

## 13.3 apktool（仅自有包）

[apktool](https://apktool.org/) 把 APK 解成可读的 `AndroidManifest.xml`、资源、以及 smali。本书只允许对**第 12.1 节那三种包**做解码，目的是看结构和资源，不是改包重签。

典型用法：

- 解码后读 Manifest：包名、`versionCode`、导出组件、是否有 Debug 才该存在的入口。
- 看 `res/`、`assets/`：渠道开关、内置 Host、`.proto`、证书或 pinning 哈希。和第 9 章抓到的 Host 对一下，常比在 DEX 里搜更快。
- 需要核对资源 ID、二进制 XML 时用它；日常版本信息用 APK Analyzer 往往够。

**不要用 apktool 做的事：**

- 改 smali / 资源后重打包、对齐、重签，用来「绕过」登录、许可、证书固定或完整性校验——即便对象是自己的 Demo，正确做法也是改源码、走 CI，而不是补丁商店包。
- 对第三方 APK 解码「只是看看」。解包是改包的第一步，来源红线在第 12.1 节已经划过。
- 把重打包后的 APK 装到非实验设备，或当成上架产物。

迭代 Demo 行为：改仓库 → CI 出新构建 → 再抓包。apktool 是读包工具，不是你们的发布流水线。

## 13.4 JEB 等能力边界

静态阅读还可以碰到这些名字。采集工程里它们是**可选的放大镜**，不是默认栈。

| 工具 | 常被用来做什么 | 本书里的边界 |
|------|----------------|--------------|
| [JEB](https://www.pnfsoftware.com/jeb/) | 商业反编译；交叉引用、图、部分混淆场景比 jadx 顺 | 授权包上读 Java/DEX；不提供商业壳的脱壳步骤 |
| [Ghidra](https://ghidra-nsa.org/) / IDA 等 | 反汇编 native | 只分析自研 / 教学 so（第 17 章）；不从第三方 so 抽密钥 |
| Android Studio APK Analyzer | 官方看包结构、大小、DEX 列表 | 优先用它完成 12.3 的地图 |
| dex2jar + JD-GUI 一类老组合 | 历史方案 | 新工作默认 jadx；不必为了教程再搭一套 |

能力边界比许可证更重要：**反编译器吃的是明文 DEX。** 壳把真 DEX 藏起来时，JEB 和 jadx 一样停在 stub。这时换未加固 Debug 构建或自研教学壳（第 14 章），不要换更贵的 GUI。

付费套件也不能把合作测试包变成「可以任意改」。对方书面范围写到「只读分析」，就不要重打包。分析结果进第 18 章元数据：工具名、版本、包哈希，方便复现的是阅读路径，不是一次不可重复的手工点击。

## 13.5 同一 Demo 打开主路径

把第 9–10、12 章和本章串成一条可重复的路。对象：你们 CI 打出的 Demo APK，与**本次抓包**同一 `versionCode`（先用历史版读懂时，抓包也要用那一版，再拿当前版对照，见 13.6）。

1. **对哈希。** SHA-256、签名指纹、构建号与 10.1 记录一致。不一致就换包，不要开始搜。
2. **APK Analyzer（或 apktool 解码）确认地图。** 包名、有无 `lib/*.so`、`assets/` 里有没有 Host / proto。一页纸沿用 12.3。
3. **jadx 打开同一 APK。** 搜索列表接口的路径或不变量头名（10.1、10.2）。
4. **落到拼请求的代码。** 记下类与方法（有 `mapping.txt` 则写还原后的名字）。标出：哪些字段在 Java 里、是否调用 native。
5. **和抓包并排。** 字段名、是否每次变、是否像 ts / nonce / hash，写进 10.2 的变化表。能对上 Java 拼接的，补进第 10.3 节脚本；进 native 的，停在「调用了某某 JNI」，不要在 jadx 里猜 so。
6. **三条结论写回接口文档：** 调用点、Java 侧能确认的规则、未知项（壳 / so / 仅运行期才有）。未知项分别指向第 14、16、17 章，而不是在本章加工具。

主路径的产出是**补全后的 10.1 文档**，不是一份反编译工程。下一次升版：换新构建，从第 1 步再走；字符串搜不到再考虑混淆还原（第 15 章）或运行期对照（第 16 章）。当前包已经加固或混淆到读不动，先试 13.6 的历史构建，再上第 14–16 章。

## 13.6 历史版本：弱防护与还活着的旧接口

**提醒：静态分析不必死盯最新包。** 同一产品在 CI 里的旧构建、你们自己上架过的旧版、合作方交付的旧测试包，都是合法对象（来源纪律同第 12.1 节）。历史版本常常更好读，也常常暴露「新客户端已经不用、服务端还没关」的接口。

旧构建上常见的差别：

- **防护更弱。** 尚未加壳、R8 / 混淆未开或很浅、证书固定还没做、签名还在 Java 里。jadx 能搜到路径，第 10.3 节更容易对上。
- **协议更简单。** 列表还在 REST + JSON，后来才改 gRPC / 字段进 so；旧版把骨架看清，再 Diff 当前版。
- **旧接口还活着。** 新包已经改调 `/v2/`，服务端若仍接受 `/v1/`、旧 Host、无签名的旧头，旧客户端（或按旧文档写的脚本）仍然能拉数。对采集这是捷径，对接口所有者这是该下线的负债（第 18 章钉版本、强更）。

建议顺序：

1. 在 CI 归档里取一枚**仍能打到同一套测试环境**的旧 Demo（哈希、构建号照记）。
2. 用那一版抓包 + 走 13.5，写出 10.1 文档。
3. 再打开**当前**构建对照：路径是否还在、签名是否升级、调用是否进了 native 或壳。文档里钉两个 `versionCode`：分析用的、采集跟的。
4. 若你控制服务端：旧路径该关、该鉴权、该催升级，不要长期靠「历史接口好爬」过日子。

旧客户端对着新服务器不一定通：强更、证书、最低版本号都会拦。读得懂不等于当前环境还能采。采集脚本最终要跟**授权范围内仍被接受的协议**，而不是永远钉死在某次漏洞窗口。

**不要做的：** 到第三方市场扒别人的历史 APK 去打别人的生产接口。旧版安全弱、旧接口没关，不能改变第 1.5、12.1 节的来源红线。

出门考（自有 Demo APK + 已有一条列表抓包）：

1. 写出本题用的工具链（Analyzer / jadx / apktool 各做了什么），并声明包来自 CI、自有上架或合作测试。
2. 在 jadx 里用路径或头名定位到拼请求的方法；把方法名写进 10.1 文档。
3. 用 Analyzer 或 apktool 指出：协议相关配置在 DEX、assets 还是 `lib/`。若在 so，写明「留给第 17 章」，不要继续砸。
4. 说明你**没有**对第三方包解码，也没有 smali 补丁重签。
5. 写明分析用的是当前构建还是 CI 历史构建；若用了旧版，对照当前包：旧接口是否仍被服务端接受，采集跟哪一个 `versionCode`。

通过即可。下一章讲加固在解决什么、加壳后静态阅读会怎样，以及只在自研教学壳上做实验。

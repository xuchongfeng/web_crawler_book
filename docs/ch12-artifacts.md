# 第 12 章 源码与制品从哪来

第五部分从这里开始。第四部分已经能在 Demo 上抓包、写协议、用 UI 触发。分析客户端，是为了**对照「请求从哪发出、字段怎么来」**，把结果回流到第 10、18 章的文档，不是为了拆别人的生产包。

制品只来自三种地方：你们的 CI、你们自己上架的包、合作方书面提供的测试包（第 1.5 节）。商店里随便下一个、第三方 APK 站上下一个，不进分析台。jadx、apktool 的用法在第 13 章；加固和 so 在第 14、17 章。

有仓库源码时，先读源码和 Debug 日志，再打开包。包是「当时上架的那一份」，用来钉版本，不是默认入口。

## 12.1 CI、自有上架包、合作测试包

每份拿来分析的文件，都要写得清**从哪来、谁签的名、对应哪个 Git 提交或构建号**。

| 来源 | 是什么 | 适合干什么 |
|------|--------|------------|
| CI 制品 | 流水线打出的 Debug / Release，带 build id | 日常对照、和第 9 章抓包同一构建 |
| 自有上架包 | 你们传到应用商店、企业分发的那一档 | 钉「线上真实协议」；分析前确认就是这次上架的编号 |
| 合作测试包 | 合同或工单交付、对方允许分析的包 | 只在授权范围内看；密钥和加固策略仍按对方红线 |

三种都要留哈希（SHA-256）和签名证书指纹，和抓包记录里的 App 版本对上。对不上，先换包，不要开始还原。

**不要当来源的：** 网盘分享的「破解版」、聚合市场扒的包、同事私人手机上拷出来且说不清渠道的安装包。来源说不清，分析结果不能进采集系统（第 18 章要元数据）。

源码仓库是更早的来源：协议、`.proto`、验签函数在仓库里时，第 10.3 节已经够用。第五部分处理的是「只有包、或要核对包和源码是否一致」。

## 12.2 APK / AAB / 渠道包

Android 上你最常碰到这几件容器。名字不同，分析前先认容器，再解内容。

**APK。** 一个 zip：`AndroidManifest.xml`、`classes*.dex`、`lib/`、`assets/`、`res/`、签名目录。Debug 和 Release 都可能是 APK。模拟器直接装的多半是它。

**AAB（Android App Bundle）。** 上架给商店的交付件，不是直接安装文件。本地分析通常用 Play / 你们 CI 打出来的**通用 APK 或分 ABI 的 APK**，不要对着 AAB 当「已经能装的包」。拆出来的 split（`base`、`xxxhdpi`、`arm64-v8a`）要成套，缺了 so 或资源，对照抓包会误判「没有 native」。

**渠道包。** 同一套代码，不同渠道改 `channel`、替换 `assets` 里的配置、或打进不同的应用 ID。采集必须钉渠道：协议 Host、开关、甚至是否加固，都可能不一样。文档里写 `applicationId` + `versionName` + `versionCode` + 渠道名，不要只写「最新版」。

iOS 的 ipa、鸿蒙的 hap 同一纪律：只分析你们构建或对方交付的那一份；容器是 zip，里面是可执行文件、资源、签名。具体工具链按端分开，原则不变。

## 12.3 Manifest、组件、DEX、lib、assets

打开包之前先有一张地图，避免第 13 章一上来就全局反编译。

**Manifest。** 包名、版本、权限、组件（Activity / Service / Provider / Receiver）、deeplink。采集关心的是：网络权限是否正常、有没有导出得过宽的调试组件（Debug 才该有）、主 Activity 是不是你以为的那一个。

**DEX。** Java / Kotlin 字节码。REST 客户端、JSON 字段名、部分签名拼接，常在这里。混淆后类名无意义，对照抓包里的路径和头名（第 10.1 节）比对着「猜类名」快。

**lib/。** `.so`，按 ABI 分目录。Protobuf 编解码、HMAC、设备摘要，有的会进 native。本章只记：**有没有 so、哪个 ABI、导出符号以后第 17 章再看**。不要一见 so 就当「必须砸」。

**assets / res。** 证书、频道配置、内置 `.proto` 或证书 pinning 的哈希、WebView 的本地页。有时列表 Host 写在配置里，不在代码里。和抓包 Host 对一下，能少走很多弯路。

地图的产出是一页纸：这个构建里，协议相关的东西大概在 DEX、so 还是 assets。第 13 章按这页选工具。

## 12.4 先判断有没有稳定接口

分析有成本。打开 jadx 之前先回答：

1. **第 9–10 章是否已经能稳定拉数？** 能，则第五部分只做抽查：包和文档是否一致、升版有没有偷偷改签名。不要为了「看起来专业」把整包反编译一遍。
2. **有没有官方 / 合作 API？** 有，则回到第 1.3 节，客户端分析不是主路径。
3. **请求是否只在客户端算出来、服务端无文档？** 且对象是自有或授权包：才值得往第 13 章走。目的仍是补接口说明，不是通读代码。
4. **一打开就是加固壳、没有明文 DEX？** 记现象，换教学壳或 Debug 未加固构建（第 14 章）。不要在这里开始找商业脱壳教程。

判断句：**包是证据，接口是产物。** 证据对不上版本就换包；产物已经够用就停。商店里别人的包，即使「只是看看结构」，也不要当练习场。

出门考（自有 CI 打出的 Demo APK 或你们上架的包）：

1. 写下构建号、SHA-256、签名指纹，和一次抓包记录对上。
2. 说明这是 APK、AAB 衍生安装件还是渠道包；渠道名写进文档。
3. 一页纸标出：Manifest 包名版本、有无 so、assets 里有没有 Host / proto。
4. 用 12.4 的四问决定：停在第 10 章，还是进入第 13 章。写出为什么。

通过即可进第 13 章。工具为任务服务：先有「要对照哪条请求」，再打开 jadx。
